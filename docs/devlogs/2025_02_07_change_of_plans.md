# Change of Plans regarding this project
This project started with several assumptions about how to provide a good, maintainable, battery-included experience in code generation.
There is already a vast selection of tools that translate OpenAPI back and forth to code and other use cases.
I haven't looked at every tool, but I have at least some idea of the landscape and different approaches.
Standard tools target a wide audience and use cases, and are often very flexible and customizable, which is generally a good thing.
But they come with limitations. Limitations that are hard to tackle when your mind is bouncing within a box framed by the tools and their capabilities.

This project started with me wanting to explore and push the limitations of translating OpenAPI from the ground up while
acknowledging existing solutions and especially the work of fellow devs in the ecosystem.
I will keep looking at standard tooling, but I will also keep getting my hands dirty to gain a better understanding of the problem and solution space. Maybe at some point, I will bring new ideas or better recognize good and bad ideas when it comes to the task of using OpenAPI specs for our daily business.

Before going into details about the assumptions and limitations, let me say what will change.

## What will change?
### Goal
I will be building a custom OpenAPI code generator for TypeScript from scratch, which will focus on generating TypeScript code and Zod schemas. However, my focus will be on the intermediate representation model used for generating types, schemas, and utilities. 

### Packages
The IR transformer will become a dedicated tool package. The generators will live in a single package so I can easily activate synergies between generators while keeping fast iteration cycles on the problems.
I will reduce all CLIs for generators to just one to reduce maintenance effort when extending features.

### Structure
Code generation will split into four main boundaries: Model, Marshaling, Client, Server.
- Model will provide TS types while supporting features to translate to inferred Zod schemas.
  - This will be especially useful when we need to explicitly declare TS types in Zod in recursive types or very large APIs.
- Marshaling will include Zod schema generation and other utilities to parse or validate data at runtime.
- Client will depend on Model and Marshaling to generate client code for making requests to an API.
- Server will depend on Model and Marshaling to generate server code for handling requests and responses.

### Challenges
There are upcoming challenges in interpreting OpenAPI 3.1 and 3.2, especially for supporting different ways of expressing polymorphism and inheritance. At this point, I am not sure if I will just provide a formatter as pre-processing before creating the IR or if the parser / interpreter will just support it.

Bundling depends on core functionality provided by redocly/openapi-core, which is a great library for parsing and validating OpenAPI specs. However, I will assess maintenance effort since the core is an internal library that keeps changing in ways that may break our code. I will also look into alternatives if the maintenance effort becomes too high.

I will keep trying to reduce the number of dependencies to reduce maintenance effort.

### AI LLMs
So far, I haven't used much AI assistance beyond "Googling" in this project, which will change. I will be using AI LLMs to assist me in the development process, especially for generating code snippets, documentation, and tests. However, I will not rely on them for critical parts of the codebase or for making architectural decisions. I will also be careful to review and test any code generated by AI LLMs to ensure it meets our standards and requirements.

## The Why?

So, I've spoken of what will change and about assumptions and limitations, but I haven't really gotten into detail, which I will now do.

### Limitations on building upon existing OpenAPI Code Generator
I assumed we can just stand on the shoulders of existing OpenAPI code generator tools, which rely on extensive intermediate representation models flavored with a plugin system based on a combination of code and customization over templates.  

From my recent experience, this works quite fine using TypeScript capabilities to parse and modify generated code.
However, it is just way too slow! So slow, that it fills my rage-driven development fuel over time when developing on this project, which led me to this project in the first place.

Another pain point is synergy between different code generators. Working on Zod integration and other code gens, I have seen myself more and more plunging and fighting with integrations of TS types and Zod inferred types.
I like things to be consistent. When I use, for example, Zod for parsing, then we must depend on the output types
because we process data at runtime, and the types may change.

This becomes clear in this example where we use `z.default`:
```typescript
    type Pet = { name: string; canFly?: boolean };
const petSchema = z.object({ name: z.string(), canFly: z.boolean().optional().default(false) });

const tsPet: Pet = { name: "Fluffy" };
const parsedPet = petSchema.parse(tsPet);

const tsCanFly: typeof tsPet.canFly = undefined;
// @ts-expect-error canFly is set by default, thus becomes required
const zodCanFly: typeof parsedPet.canFly = undefined;
```

So generally, I want my TS generated types to adjust predictably to the use cases I implement.
The costs of having "weak" types not accounting for changes in the data structure are too high for me.
An optional type must be handled in strict TS. This is a waste of time and mental energy when we have handled optionality of a property in the schema but failed to express this in the resulting types.

### Reaching battery-included state
I assumed I already had a complete understanding of what is needed to reach a battery-included state.

Working on the project widened my understanding of the problem space and solution space.
One key understanding is the boundaries in code generation. This is what other projects already got mostly right.
We need to separate models from marshaling and client / server code generation. This allows us to have a clear separation of concerns and to reuse the same models for different use cases.

However, in practice devs (myself included) just want to have a client or a server and reliably get the data in their application. Models on their own are not that useful since they may need to account for the environment where they are used.
Devs are working with different frameworks like express, axios, fetch, react-something, spring, etc., and have different requirements regarding the generated code.

I already knew about this and I tried having one generator that generates code so it is useful for every environment.
But it just isn't enough, not for me at least.
